The main session is the **lead**: it owns scoping, the variant mockups,
the decision record and communication with the user. Building a decided
mockup page into `mockups/` can be delegated to `implementer` subagents
(`.claude/agents/implementer.md`, runs on Sonnet). A session started by
an orchestrator session also follows the `package-sessions` skill (start
prompt, reporting back).

Talk to the user in their language (German); everything written to the
repo stays English (CLAUDE.md).

## Model choice

| Work | Model |
|---|---|
| Every orchestrator session: scoping with the user, variant mockups, the decision record, verification, starting packages and checking their reports | **Opus** |
| Building a decided mockup page from a clear brief, extending the shared sample data, screenshots | **Sonnet** (`implementer` default) |
| Searches across many files where only the conclusion matters | **Haiku** (`Explore` subagent with `model: "haiku"`) |

- **Not on Opus?** A session that becomes an orchestrator (`from-request`,
  `from-backlog`, `orchestrate`, the orchestrator of `package-sessions`;
  not a package session, whose model its orchestrator picked) checks its
  own model first (`get_session` → `session_context.model`). Anything but
  Opus: stop before scoping, tell the user in one line, and offer to hand
  over to a new Opus session (`create_session` with the request and
  everything found so far in the start prompt). Go on only after the user
  confirms either way.
- Escalate, don't start high: a step that still fails after two
  correction rounds on Sonnet goes to a fresh implementer with
  `model: "opus"`, together with what was tried.
- Delegate only where it saves more than it costs: a subagent starts cold.
  A small mockup change, or one the lead has just designed in the variant
  Artifact anyway, the lead builds itself.

**Terms** (the user's words map to these, ask if unclear):

| Term | What it is |
|---|---|
| **Variant mockup** (Konzept-Mockup) | Interactive Artifact with 2–3 variants to decide between; never a repo file |
| **Mockup** (repo) | `mockups/<area>.html`: the decided UI, clickable, in all tiers |
| **Requirement** | An item in `docs/requirements.md`: what NoteDown does, why, where it is shown |
| **Bedienkonzept** | `docs/interaction-concept.md`: rules that hold across features |
| **Plan** | `plan-<topic>.md` in the scratchpad: steps for the implementer when a page is big |

## Phase 1 — Scope the request

- Restate the goal in a few sentences, in the user's terms.
- Read what is decided already (`docs/requirements.md`,
  `docs/interaction-concept.md`, the affected `mockups/` pages) so the
  variants build on it instead of contradicting it.
- Ask only questions whose answer changes what gets designed. Anything
  with a sensible default: pick it, state it, move on.
- Ask them all at once. When you stop for a mockup decision (phase 2), the
  other open questions go into the same message. Every stop waits for the
  user, and after an hour of waiting the session's whole context is cached
  anew when it resumes.

## Phase 2 — Variant mockup (UI decisions)

Any decision about what the user sees or how they operate it — a new
view, layout, navigation, gesture, control — starts with a variant
mockup, **and the lead stops there until the user has decided**. Skip it
for pure requirement wording with no UI consequence, or when the user
already fixed the design in detail.

How to build it: `mockup.md` in this folder (today's state, 2–3
interactive variants in all three tiers, pros/cons, one recommendation,
published as an Artifact).

After the user's decision, iterate the variant mockup if they asked for
changes; otherwise go on to phase 3 with the chosen variant as the spec.

## Phase 3 — Write down and build

1. **Decision record (lead, always itself):** the requirement in
   `docs/requirements.md` (behavior, one line why, mockup page, backlog
   `Nr`); rules that hold beyond this feature in
   `docs/interaction-concept.md`. Edit the existing section to the new
   state.
2. **Repo mockup:** build the decided variant into `mockups/<area>.html`
   (new page or update), using `mockups/shared/` for tokens and sample
   content (`PROJECT.md` → "Mockup conventions").

| Mockup work | Who |
|---|---|
| A change to an existing page, or a page the variant Artifact already contains nearly as is | **Lead itself** |
| A new page or a larger rework with a clear spec | **Implementer**, direct brief (`delegation.md`) |
| Several pages or flows, or > ~1 h of work | **Written plan** in the scratchpad, implementer gets the path and one step at a time |

- `subagent_type: "implementer"`, `run_in_background: true` unless you
  have nothing else to do meanwhile. Keep the agent's ID: corrections go
  to the **same** agent via `SendMessage`.
- **Never two agents in one checkout.** Implementers on different pages
  may run in parallel, each with `isolation: "worktree"`; the lead merges
  their branches one at a time. Two steps that both change
  `mockups/shared/` run one after another.
- **Usage budget** before each step (`usage-budget.md`).
- **Keep the user's view current:** each step gets a line in the status
  checklist; the implementer logs to `<scratchpad>/progress-<topic>.md`,
  and the lead mirrors its latest line whenever it is woken anyway.

## Phase 4 — Verify (lead, every round)

Never forward a "done" unchecked, your own included. See
`verification.md`: diff review, screenshots of every changed view in
every tier (both themes if styling changed), no page errors, decision
record matches the mockup, docs and TOCs current.

Anything off → concrete correction message to the same implementer
(what is wrong, where, expected vs. seen, screenshot path), then verify
again. Loop until clean.

## Phase 5 — Present the round

Only after verification passed:

- Run the `finish` skill: merge current `main`, checks, commit, push. No
  PR unless the user asks.
- Show the result **with screenshots** (`SendUserFile`, `display:
  "render"`, one caption each — at least one per tier), or republish the
  repo mockup as an Artifact when the user wants to click through it on
  their device.
- Short summary: what was decided, where it is written down, deviations
  from the variant mockup and why, open points / suggested next step.

A package session then reports to its orchestrator (`package-sessions` →
"Reporting back"). Then wait for the user's feedback; it starts the next
round at phase 1–3 as needed.
