The main session is the **lead**: it owns scoping, the variants, the
decision record and communication with the user. Prototype work with a
clear spec can be delegated to `implementer` subagents
(`.claude/agents/implementer.md`, runs on Sonnet). A session started by
an orchestrator session also follows the `package-sessions` skill (start
prompt, reporting back).

Talk to the user in their language (German); everything written to the
repo stays English (CLAUDE.md).

## Model choice

| Work | Model |
|---|---|
| Every orchestrator session: scoping with the user, designing the variants, the decision record, verification, starting packages and checking their reports | **Opus** |
| Prototype work from a clear brief (a decided view, a fix with known cause), extending the sample notes, tests, screenshots | **Sonnet** (`implementer` default) |
| Searches across many files where only the conclusion matters | **Haiku** (`Explore` subagent with `model: "haiku"`) |

- **Not on Opus?** A session that becomes an orchestrator (`from-request`,
  `from-backlog`, `orchestrate`, the orchestrator of `package-sessions`;
  not a package session, whose model its orchestrator picked) checks its
  own model first (`get_session` → `session_context.model`). Anything but
  Opus: stop before scoping, tell the user in one line, and offer to hand
  over to a new Opus session (`create_session` with the request and
  everything found so far in the start prompt). Go on only after the user
  confirms either way.
- Escalate, don't start high: a step that still fails after two
  correction rounds on Sonnet goes to a fresh implementer with
  `model: "opus"`, together with what was tried.
- Delegate only where it saves more than it costs: a subagent starts cold.
  Variants, which are design work, and small changes the lead builds
  itself.

**Terms** (the user's words map to these, ask if unclear):

| Term | What it is |
|---|---|
| **Prototype** (Mockup) | `app/`: the clickable web app, in all tiers |
| **Variant** | One of 2–3 switchable solutions for an open decision inside the prototype (`PROJECT.md` → "Prototype options") |
| **Requirement** | An item in `docs/requirements.md`: what NoteDown does, why, where it is shown |
| **Bedienkonzept** | `docs/interaction-concept.md`: rules that hold across features |
| **Plan** | `plan-<topic>.md` in the scratchpad: steps for the implementer when a change is big |

## Phase 1 — Scope the request

- Restate the goal in a few sentences, in the user's terms.
- Read what is decided already (`docs/requirements.md`,
  `docs/interaction-concept.md`, the affected code in `app/`) so the
  variants build on it instead of contradicting it.
- Ask only questions whose answer changes what gets designed. Anything
  with a sensible default: pick it, state it, move on.
- Ask them all at once. When you stop for a variant decision (phase 2), the
  other open questions go into the same message. Every stop waits for the
  user, and after an hour of waiting the session's whole context is cached
  anew when it resumes.

## Phase 2 — Variants in the prototype (UI decisions)

What the user specified in detail is built as specified. Where a decision
about what the user sees or how they operate it is still open — layout,
navigation, gesture, control — the lead builds 2–3 variants into the
prototype, switchable side by side, **and stops there until the user has
decided**.

How: `variants.md` in this folder (switchable under ⋮ → "Prototype" and by
URL parameter, screenshots per variant and tier, pros/cons, one
recommendation).

After the user's decision, iterate if they asked for changes; otherwise
go on to phase 3.

## Phase 3 — Write down, clean up, build the rest

1. **Decision record (lead, always itself):** the requirement in
   `docs/requirements.md` (behavior, one line why, backlog `Nr`); rules
   that hold beyond this feature in `docs/interaction-concept.md`. Edit
   the existing section to the new state.
2. **Clean up:** delete the losing variants (code, CSS, menu entries, URL
   parameter, the row in `PROJECT.md` → "Prototype options").
3. **Build what the decision still needs**:

| Prototype work | Who |
|---|---|
| Removing variants, small changes, fixes in code the lead just wrote | **Lead itself** |
| A new view or a larger rework with a clear spec | **Implementer**, direct brief (`delegation.md`) |
| Several views or flows, or > ~1 h of work | **Written plan** in the scratchpad, implementer gets the path and one step at a time |

- `subagent_type: "implementer"`, `run_in_background: true` unless you
  have nothing else to do meanwhile. Keep the agent's ID: corrections go
  to the **same** agent via `SendMessage`.
- **Never two agents in one checkout.** Implementers on separate views
  may run in parallel, each with `isolation: "worktree"`; the lead merges
  their branches one at a time. Steps that both change shared code
  (`store.js`, `main.js`, `app/js/core/`, the tokens in `app.css`) run one
  after another.
- **Usage budget** before each step (`usage-budget.md`).
- **Keep the user's view current:** each step gets a line in the status
  checklist; the implementer logs to `<scratchpad>/progress-<topic>.md`,
  and the lead mirrors its latest line whenever it is woken anyway.

## Phase 4 — Verify (lead, every round)

Never forward a "done" unchecked, your own included. See
`verification.md`: diff review, `node --test`, the changed flows driven in
the browser, screenshots of every changed view in every tier (both themes
if styling changed), no page errors, decision record matches the
prototype, docs and TOCs current.

Anything off → concrete correction message to the same implementer
(what is wrong, where, expected vs. seen, screenshot path), then verify
again. Loop until clean.

## Phase 5 — Present the round

Only after verification passed:

- Run the `finish` skill: merge current `main`, checks, commit, push. No
  PR unless the user asks.
- Show the result **with screenshots** (`SendUserFile`, `display:
  "render"`, one caption each — at least one per tier and per variant),
  plus how to open it (`PROJECT.md` → "Running it").
- Short summary: what was decided or built, where it is written down,
  open variants with your recommendation, open points / suggested next
  step.

A package session then reports to its orchestrator (`package-sessions` →
"Reporting back"). Then wait for the user's feedback; it starts the next
round at phase 1–3 as needed.
